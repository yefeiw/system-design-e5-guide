# Q7 · 票务预订系统（Ticket Booking / 秒杀）

> 难度：Medium ｜ 母题：并发资源竞争（一致性 vs 可用性）
> Hello Interview 标注的 **E5 高频题**。精髓在于：抢票的瞬间是**强一致性问题**，其余一切（搜索、展示、支付）都是干扰项。

## 1. 题目原文

"设计一个 Ticketmaster：用户搜索活动、选座位（或抢票）、下单支付。Taylor Swift 级别的开售：50 万人同时抢 5 万张票。"

## 2. 澄清问题清单

| 问题 | 意图 |
|------|------|
| 选座制（specific seat）还是抢座制（first-come-any-seat）？| 两种并发模型完全不同 |
| 允许超卖吗？（航空公司故意 105%）| **一致性要求的定盘星** |
| 下单后锁定多久？（购物车持有期）| 锁的粒度和时长 |
| 支付异步吗？ | 订单状态机复杂度 |
| 候补队列（waitlist）要不要？ | 架构的第四种答案 |

## 3. 估算演示

```
50 万人开售瞬间涌入；峰值请求 500K 用户 × 每秒刷新 1 次 = 500K QPS
可售库存：5 万张 —— 真正需要"强一致竞争"的写只有 ≤ 5 万次
结论 → 99% 的流量（浏览、刷新、查询余票）根本碰不到库存，
       只要把读和写分开，写冲突其实很小 —— 这个洞察决定整个架构
```

## 4. 高层设计

```
开售前：静态化活动页 + CDN（搜索/详情 100% 缓存，零回源）
开售中：
  用户 ──▶ 排队网关（Virtual Waiting Room：发号 + 令牌 + 心跳）
              │（按批次放行，如每 5 秒放 2000 人）
              ▼
          余票查询（Redis 缓存库存快照，秒级刷新）
              │有余票
              ▼
          下单服务 ──▶ 库存扣减（原子操作，见深挖 A）
              │成功                      │失败
              ▼                          ▼
          订单创建（15 min 支付窗口）    重新排队/候补
              ▼
          支付（异步回调）──▶ 出票（座位/票码，写库，最终一致）
```

**架构叙事**："我用**排队室把不可控的洪峰变成可控的匀速流**——用户拿号入场而不是全量打到业务层；进场的请求才碰库存。这个决定同时解决了过载和公平性（先到先得）两个需求。"

## 5. 数据模型

```sql
events (event_id, venue, onsale_at, total_seats)
seats  (seat_id, event_id, section, row, num, status)   -- 选座制核心表
       status: AVAILABLE → HELD → SOLD / 回 AVAILABLE
orders (order_id, user_id, event_id, status, expires_at)
       status: PENDING → PAID → ISSUED / EXPIRED/CANCELLED
库存计数: Redis inventory:{event_id}（抢座制用计数，选座制按 seat 行锁/乐观锁）
```

## 6. 深挖

### 深挖 A · 库存扣减的并发正确性（主菜）

**方案谱系（从低到高）**：

1. **数据库乐观锁**：`UPDATE seats SET status='HELD' WHERE seat_id=? AND status='AVAILABLE'`（CAS 语义，影响行数=1 即成功）
   - 简单正确；单行热点下 DB 可能到几千 QPS —— 配合排队限流后**往往就够用了**
2. **Redis 原子扣减**：`DECR` / Lua（查+扣原子）—— 扛 10 万 QPS
   - **关键坑：Redis 成功、DB 失败怎么办** → 异步落库 + 对账；Redis 挂了怎么办（AOF + 快照，最坏丢秒级库存状态 → 恢复时从 DB 全量重建）
3. **预扣额度到内存分段**：库存分 100 段，每段独立扣——分散热点，最后一段合并
   - 复杂度高，只在单行成为瓶颈时才上

**E5 收口**："先算真实冲突量：5 万张票最多 5 万次成功扣减，排队后并发写只有几千 QPS——**单行乐观锁就是正解**，Redis 预扣是过早优化。真正难的不是扛量，是**状态机的正确性**。"（展示"方案匹配规模"的判断力）

### 深挖 B · 锁与持有期（选座制）

- HELD 状态 + `expires_at`：15 分钟内不支付自动释放
- 释放路径：定时扫描（慢）→ **延迟队列**（Redis ZSet/LevelDB 按到期时间）→ 到期事件驱动释放
- "过期释放必须是系统的主动行为而不是等用户动作——否则黄牛脚本锁座不付款能锁死全场"

### 深挖 C · 支付的最终一致

- 订单状态机：PENDING → PAID → ISSUED，每个转换幂等（支付回调会重试）
- 支付成功但出票失败：对账任务扫 PENDING_PAID → 补偿（退款 or 人工）
- "支付网关回调至少投递一次，我的状态迁移必须幂等：`UPDATE orders SET status='PAID' WHERE order_id=? AND status='PENDING'`——又是 CAS。"

### 深挖 D · 不超卖的形式化论证

被问"你怎么保证绝对不超卖"：
> "所有路径汇到同一个串行点：每个 seat 行的 CAS。Redis 快照可以 stale（显示有余票但下单失败 → 提示重试，用户体验问题，不是正确性问题）；**展示层允许乐观，成交层绝对悲观**。不超卖的证明 = 所有成交都过了那一条 CAS UPDATE。"
（"展示乐观、成交悲观"这句话本身就是 E5 水平的总结）

### 深挖 E · 防黄牛（加分区）

- 设备指纹 + 账号风控前置（进排队室之前过滤）
- 限购（per-user 配额，下单服务内存校验 + 落库对账）
- 手机验证码拉开人类响应节奏

## 7. 红牌答案

- 上来讨论搜索架构（审题失败——这题考一致性不是考搜索）
- 用分布式锁锁整个 event（粒度灾难）而不讨论行级 CAS
- Redis 扣库存但不讲 DB 一致性
- 没有支付超时释放路径
- 用 zookeeper/etcd 选主当卖点（解决的是错误的问题）

## 8. 一分钟电梯版

"先把读写分开：静态页全 CDN、余票读缓存快照（展示层允许乐观）；洪峰用虚拟排队室整流成匀速流再进下单。成交层的正确性靠每座位一行的 CAS UPDATE（AVAILABLE→HELD→SOLD 状态机 + 过期延迟队列释放 + 幂等支付回调），Redis 预扣只有在单行热点实测不够时才加，并配对账兜底。真实冲突量只有 5 万次成功写，方案匹配规模即可，不超卖的证明是'所有成交汇于单点串行化'。搜索和推荐不是本题采分点。"
