# Q2 · 限流器（Rate Limiter）

> 难度：Easy–Medium ｜ 母题：算法深挖 + 分布式一致性
> 题目小，但**算法层四档对比 + 分布式时钟问题**能一路问到 E5 的知识底。

## 1. 题目原文

"设计一个 API 限流器，防止滥用。要支持每用户每秒/每分钟 N 个请求。"

## 2. 澄清问题清单

| 问题 | 意图 |
|------|------|
| 限谁的维度？（IP / 用户 / API key / 全局）| 决定限流键设计 |
| 硬限还是软限？（超了返回 429 还是排队）| 可用性取向 |
| 分布式限还是单机限？ | 本题分水岭 |
| 规则要动态下发吗？ | 引入配置中心 |
| 限流的语义：平均速率 vs 突发容量 | 直接指向算法选择 |

## 3. 估算（简短，本题不在数字上纠缠）

"假设 100K QPS 峰值、2000 万活跃 key——限流判断本身必须 <1ms P99 且不成为新瓶颈，所以它必须是**内存级操作**，这是本题第一设计约束。"

## 4. 高层设计

```
                        ┌────────────────────────────┐
客户端 ──▶ API Gateway ──▶ 限流中间件（进程内）──▶ 业务服务
                          │  ↑ 规则下发（配置中心）
                          │  ↕ 异步同步计数（Redis，最终一致）
                          └────────────────────────────┘
被限请求 ──▶ 429 + Retry-After ──▶ （可选）Kafka 记录被限事件
```

**关键架构决策**："限流在**网关/中间件进程内做**，Redis 只做跨实例的计数收敛（异步/准同步）。每请求一次 Redis 同步调用会把限流器自己变成 20 万 QPS 的 Redis 集群——得不偿失。"

## 5. 数据模型

Redis：`rate:{user_id}:{window_start}` → 计数器 / 令牌桶状态（Lua 脚本原子读改写）。
规则中心：`rule_id → {key_template, algorithm, limit, window, burst}`。

## 6. 深挖

### 深挖 A · 四种算法（必考，背成对比表）

| 算法 | 原理 | 优点 | 致命缺点 |
|------|------|------|---------|
| 固定窗口 | 每 N 秒计数清零 | 最简单、省内存 | **窗口边界突发**：两个窗口交界可放行 2N |
| 滑动窗口日志 | 记录每个请求时间戳 | 精确 | 内存 O(QPS×窗口)，大流量不可用 |
| **滑动窗口计数** | 当前窗口计数 ×(1-流逝比例) + 上窗口计数 ×流逝比例 | 近似平滑、O(1) 内存 | 两窗口交界处仍是近似 |
| **令牌桶** | 桶容量 b，速率 r 匀速放令牌 | **允许受控突发**、业界默认（Guava/WFF） | 参数语义要讲清（b 和 r 分开） |

E5 表达："默认答案令牌桶——因为它把『平均速率』和『突发容量』分成两个正交参数，符合真实流量形态。如果业务明确不允许任何突发（比如保护脆弱下游），换漏桶整形。Cloudflare 生产用的是滑动窗口计数（他们的博客值得读）。"

### 深挖 B · 分布式：同步 vs 异步（本题的 E5 分水岭）

**同步模式**（每请求查 Redis + Lua 原子判断）：
- 精确，但 Redis 成关键路径——挂了限流器全挂
- 缓解：Redis 集群 + 一致性哈希分 key

**异步模式**（本地判断为主，定期和 Redis 对账）：
- Redis 挂了照样限流（降级为单机限流）→ **可用性优先**
- 代价：多实例合计会**短暂超限**（比如允许 1.1N）——"对防滥用场景，10% 的超限换取限流系统自身永不成为故障点，这个 trade-off 我主动接受并写进设计文档。"

被问"必须精确怎么办"→ 同步模式 + Redis HA + "精确限流本身就是个强一致需求，成本要讲给业务听"。

### 深挖 C · 时钟与公平

- 各实例时钟漂移对窗口计算的影响（用单调时钟 + Redis 中心时间戳校准）
- 滑动窗口的内存问题在多 key 下被放大 → 分片按 key 哈希
- 冷启动：服务重启后本地计数清零 → 从 Redis 快速预热

### 深挖 D · 限流之后的响应设计

- 429 + `Retry-After` 头 + `X-RateLimit-Remaining`（API 友好性，很多 senior 都漏）
- 分层限流：网关层粗粒度（IP）+ 服务层细粒度（user+endpoint）
- 被限事件进 Kafka → 攻击检测 / 规则调优

## 7. 红牌答案

- 只会"固定窗口计数 + Redis INCR"一档，说不出边界突发问题
- 把 Redis 同步调用放关键路径却不讨论它挂掉的场景
- 不知道令牌桶的 burst 与 rate 是两个参数
- 没有降级方案（限流器自己把全站打挂 = 设计事故）

## 8. 一分钟电梯版

"进程内令牌桶做判断（r 控均值、b 控突发），Redis 做跨实例计数收敛——同步模式精确但把 Redis 放进关键路径，我默认异步对账 + 降级单机限流，接受 10% 超限换可用性，防滥用场景这个 trade-off 成立。规则从配置中心下发支持热更新，被限请求带 Retry-After 返回，事件进 Kafka 做分析。如果下游是计费类必须精确，我会换同步 + Redis 集群并把成本讲清楚。"
