# 01 · 什么是 System Design 面试

> 本章回答三个问题：这场面试**到底在考什么**、有**哪几种形态**、面试官**按什么标准打分**。

## 1. 各家权威定义

### Design Gurus（Grokking 系列出品方）

> "系统设计面试是一个开放式技术面试：你被要求从零开始设计一个大规模分布式系统。它没有唯一正确答案——评估的是你**澄清需求、处理模糊性、并做出关键架构决策**的能力。"

这是最标准的教科书式定义。注意两个关键词：**开放式**（意味着主动权在你）和**没有对错**（意味着评分的是过程）。

### Hello Interview（FAANG 前面试官团队，目前最好的免费资源）

他们不纠结定义，直接给评分表。他们对 System Design 面试的理解是：

> 一场 45 分钟的协作设计会话，面试官扮演资深同事/评审者的角色，看你如何把一个模糊的产品需求变成一个可辩护的技术架构。

### System Design Primer（GitHub ~280k star）

> "学习如何设计大规模系统。帮助你成为更好的工程师，并附带面试准备。"

定位是资源总纲：按主题（负载均衡、一致性、CDN、缓存……）组织知识，附真题与参考答案。适合当地图用，不适合当路线用。

### System Design Handbook

强调一个所有 senior 都该刻在脑子里的观念：

> **不存在完美的设计。每一个选择都有代价。** 好的设计不是「最优解」，而是在给定约束下最合理的折中。

另外一个冷知识：Meta 内部把系统设计轮叫 **"Pirate" 轮**（因为主持这轮的面试官小组代号 "Pirates"），近年又分化出偏 API/产品设计的 **"Pirate X"**（详见 [08 公司风格指南](08-company-guides.md)）。

## 2. 面试的四种形态

按 Design Gurus 的分类（E5 后端方向 90% 是第一种）：

| 类型 | 考什么 | 典型题 | 出现场景 |
|------|--------|--------|---------|
| **后端 / 分布式系统设计** | 可扩展架构、数据建模、瓶颈分析 | 短链、Feed、票务系统 | 后端/全栈 E5 主战场 |
| **API 设计** | REST 语义、资源建模、版本化、分页 | 设计 Twitter API、支付 webhook | 部分公司独立一轮 |
| **前端系统设计** | 组件架构、状态管理、渲染性能 | 设计 Netflix 播放器、表格组件 | 前端岗专属 |
| **OO 设计（OOD）** | 类图、设计模式、领域建模 | 设计停车场、象棋 | 多见于中小厂 |

> Meta 特别提示：E5 可能遇到 **Product Architecture 轮**（偏 API/数据建模/用户流程）而非传统 System Design 轮（偏基础设施/扩展性）。评分标准相同，但深挖方向不同——见过太多人按纯后端准备结果撞上 Product Architecture。

## 3. 四维评分标准（Hello Interview Rubric）

这是目前公开最接近大厂内部评分表的框架，**四个维度、按百分比加权**：

### 3.1 Problem Navigation（问题导航）— 30%

- **主动澄清**：规模（QPS / DAU / 数据量）、读写比、一致性要求、延迟预算、客户端类型
- **收敛范围**：明确说出「我打算先做 X，Y 放到 follow-up」——面试官最怕你什么都想做
- **对齐定义**：把模糊词翻译成具体功能（「快」是多快？「活跃用户」怎么定义？）

### 3.2 Solution Design（方案设计）— 30%

- 高层架构清晰：画得出组件图，说得清数据流向
- 能覆盖核心功能与非功能需求（可用性、扩展性、延迟）
- **方案与需求匹配**：日活 1 万的系统不要上来就分库分表 + 多区域容灾（over-engineering 在 E5 是减分项）

### 3.3 Technical Depth & Differentiation（技术深度）— 20%

- 深挖至少一个子系统到实现层面：存储引擎选型、索引设计、一致性协议、故障模式
- 能讲清 trade-off：「选 A，代价是 X，因为我们的场景里 X 可接受而 Y 不可接受」
- 展现超出「标准答案」的理解：知道常见方案的坑（如 Redis 缓存失效风暴、Kafka 分区倾斜）

### 3.4 Communication & Collaboration（沟通协作）— 20%

- 结构化表达：先总后分，随时让面试官知道你在哪一层
- **接受引导**：面试官纠偏时快速调整而不是硬扛（面试官的 hint 是礼物）
- 驾驭白板：图要能读懂，边画边讲

> 注意 30/30/20/20 这个结构传递的信号：**「走对了流程」和「方案合理」占 60 分，比「技术多硬核」更重要**。很多人挂在这一关不是因为技术差，而是因为流程失控——不问需求直接画图，或者被自己带进死角出不来。

## 4. 面试官在打分时实际在想什么

把 rubric 翻译成面试官的内心 OS：

| Rubric 条目 | 面试官内心 OS |
|------------|--------------|
| 主动澄清 | 「我还没给需求，他就把该问的都问了」 |
| 收敛范围 | 「他知道什么重要什么不重要，像个做过线上系统的人」 |
| 方案匹配需求 | 「这个规模这个方案刚好，不过度也不过简」 |
| 深挖 trade-off | 「他不只是读过 ByteByteGo，他知道这些组件真实的坑」 |
| 接受引导 | 「我 hint 了一句他立刻调头，合作起来会很舒服」 |

**E5 的分水岭**：E4 面试官拉着你走完全程也能过；E5 必须是你驱动全程，面试官只是在 review 你的设计。

## 5. 一场 45 分钟面试的真实解剖

```
0:00–2:00   面试官介绍题目（很模糊的一句话）
2:00–7:00   你澄清需求、估算规模、定义范围     ← Navigation
7:00–20:00  高层设计：组件图 + API + 数据模型  ← Design
20:00–38:00 深挖 2–3 个子系统（面试官选方向）  ← Depth
38:00–43:00 瓶颈、监控、故障、扩展、收尾      ← Depth + 收尾
43:00–45:00 你的提问
```

每一阶段的具体打法见 [03 表达框架](03-delivery-framework.md)。
