# 04 · 估算与必备数字（Back-of-Envelope）

> 估算的作用不是算准，是**用数字框定设计空间**。E5 面试里一句「按 100M DAU、读写比 100:1，读 QPS 峰值约 100K，单库 MySQL 扛不住，所以这里必须分片」值 10 句形容词。

## 1. Numbers to Know（先背这张表）

### 1.1 延迟数字（Jeff Dean 经典表，2020s 更新版）

| 操作 | 量级 | 记忆锚点 |
|------|------|---------|
| L1 cache 命中 | ~1 ns | — |
| 互斥锁加锁 | ~15 ns | — |
| 内存随机读 | ~100 ns | 1 KB 数据 |
| **SSD 随机读** | **~150 µs** | 比内存慢 1000× |
| 同机房 RTT | ~0.5 ms | — |
| **跨可用区 RTT** | **~1–2 ms** | 同区域 |
| **跨区域 RTT（美东↔美西）** | **~60–80 ms** | 光速物理极限 |
| HDD 寻道 | ~10 ms | — |
| 顺序读 1 MB（SSD） | ~1 ms | — |

**面试金句**："跨区域一次 RTT 够内存读 60 万次——这就是为什么多区域同步复制是最后手段。"

### 1.2 可用性换算

| 9s | 年停机 | 用法 |
|----|--------|------|
| 99% | 3.65 天 | 不能叫 HA |
| 99.9% | 8.7 小时 | 一般线上服务底线 |
| 99.99% | 52 分钟 | 需要自动故障转移 |
| 99.999% | 5 分钟 | 需要消除一切人工介入 |

**金句**："我们说 99.95%，意味着月度预算 22 分钟——每次发布耗 5 分钟的话，发布故障最多容忍 4 次。"

### 1.3 单机容量直觉（2020s 硬件）

| 资源 | 单机量级 |
|------|---------|
| 内存 | 64–256 GB |
| SSD | 4–16 TB |
| 网卡 | 10–25 Gbps ≈ 1–3 GB/s |
| Web 服务器并发连接 | ~10K–65K（端口/内存限制）|
| 单 MySQL 实例安全写 QPS | ~5K–10K（普通硬件、简单写）|
| 单 Redis 实例 | ~100K ops/s |
| 单 Kafka broker | ~100K+ msg/s（小消息）|

**这些数字决定「什么时候必须上分布式」**——比如写入 QPS 估出来 50K，单库必挂，你就有了分片/队列削峰的数字依据。

## 2. 估算流程（4 步，2–3 分钟讲完）

1. **用户规模** → DAU（题目给的或假设）
2. **读写 QPS** → 人均操作次数 × DAU ÷ 86400，再乘峰值系数 ×3–5
3. **存储** → 单条记录大小 × 日增条数 × 保留年限（**别忘了索引和副本的放大系数，通常 ×2–3**）
4. **带宽** → QPS × 平均请求/响应大小

### 完整示例：短链服务（题目：100M DAU，人均 5 次读 0.1 次写）

```
读 QPS = 100M × 5 / 86400 ≈ 5,800 QPS，峰值 ×3 ≈ 17K QPS
写 QPS = 100M × 0.1 / 86400 ≈ 115 QPS，峰值 ≈ 350 QPS
存储   = 500 bytes/条 × 4B 条/年 ≈ 2 TB/年（含索引 ×2 ≈ 4 TB）
带宽   = 17K × 1 KB ≈ 17 MB/s 读出 —— 很轻
结论   → 读需要缓存（17K QPS 单库 + 每次回源扛不住），写完全无压力，
         存储单分片扛得住 → 这是"读重写轻"的教科书场景
```

注意最后一句：**估算必须落到设计结论**。算完不说话等于白算。

## 3. E5 级别的估算加分项

### 3.1 主动声明假设的误差范围

> "DAU 我假设 100M，哪怕差一个量级到 10M，结论不变——因为瓶颈在缓存而不是数据库行数。"（展示估算的稳健性思维）

### 3.2 算「钱」

> "存储 4 TB/年，S3 是 $0.023/GB/月，一年存储成本不到 $1,200——成本不是约束。但如果有图片，对象存储 + CDN 才是大头。"

### 3.3 算「人」

大厂面试官喜欢听容量规划落到运维：
> "17K QPS 峰值，单实例扛 3K，需要 6 台 + N+2 冗余 ≈ 8 台，一个 ASG 就够了，不需要多区域。"

## 4. 常见坑

| 坑 | 修正 |
|----|------|
| 忘乘峰值系数（用平均 QPS 定容量） | 平均 ×3–5 才是容量目标 |
| 忘副本和索引放大 | 存储直接 ×2–3 |
| 单位错乱（GB/Gbps/GB/s 混用） | 白板顶上写清单位再动笔 |
| 估完不落地 | 每个数字后面跟一句"所以……" |
| 精确到小数 | 保留 1–2 位有效数字，展示的是量级思维 |

## 5. 练习清单（每天 10 分钟，练两周）

给这些场景口算 QPS / 存储 / 带宽，限时 3 分钟：

1. Twitter Feed：200M DAU，人均刷 20 次
2. 聊天系统：50M DAU，人均 40 条消息，消息保留 1 年
3. 视频站：100M DAU，人均 30 分钟，平均码率 2 Mbps
4. 日志系统：10K 服务器 × 每台 100 logs/s × 500 B/log
5. 广告点击：1B impressions/day，CTR 1%，点击记录 200 B

答案自己算，重点是把「数字 → 设计结论」的最后一句话练成本能。
