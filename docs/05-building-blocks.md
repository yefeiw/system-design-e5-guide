# 05 · 核心构件（Building Blocks）

> 每个构件按两层组织：**E4 层**（知道是什么）一句话带过；**E5 层**（选型理由 + trade-off + 真实的坑）是你要练到脱口而出的部分。

## 1. 负载均衡（Load Balancer）

**E4 层**：L4（TCP）按连接分发，L7（HTTP）按请求分发，算法有轮询/最少连接/一致性哈希。

**E5 层**：
- **有状态 vs 无状态**：一致性哈希解决「同一用户落到同一节点」——用在连接粘滞、缓存分片；代价是节点增删时的 rehash 抖动（virtual nodes 缓解）
- **健康检查与摘除**：多久探测一次、几次失败摘除、**摘除后流量去哪**（雪崩风险）
- **全局负载均衡**：GeoDNS / Anycast 把用户引到最近区域；「区域挂了 TTL 内切不走」是经典坑
- 现实中通常双层：云 LB（ALB/Envoy）+ 客户端侧负载均衡（service mesh）

**金句**："LB 本身要无状态 + 健康检查，否则它自己成了单点——我们用 N+1 个 LB + VRRP/Anycast。"

## 2. 缓存（Cache）

**E4 层**：本地缓存 vs 分布式缓存（Redis/Memcached），cache-aside 模式。

**E5 层**——按四个问题组织：

### 2.1 放什么模式
| 模式 | 适用 | 坑 |
|------|------|-----|
| Cache-Aside | 默认选择 | 失效窗口；首次加载穿透 |
| Write-Through | 读多、能接受写延迟 | 写路径变慢；冷数据占内存 |
| Write-Behind | 写 QPS 高 | **丢数据窗口**——计费类不可用 |
| 逻辑过期 | 热点 key | 返回 stale 数据要业务可接受 |

### 2.2 失效怎么办
- **缓存穿透**（查不存在的 key）：布隆过滤器 / 缓存空值
- **缓存雪崩**（同时失效）：TTL 加随机抖动 / 逻辑过期 / 多级缓存
- **缓存击穿**（热点 key 过期瞬间）：singleflight（合并回源）/ 互斥锁回源

### 2.3 一致性多强
- 「先更新 DB 再删缓存」是主流答案，但**仍有窗口**——讲得出这个窗口及「延迟双删/订阅 binlog（CDC）」的补法，就是 E5 水平
- 追问终极版：「缓存和 DB 永远强一致做不到，只能收敛——你的业务能接受多长的收敛窗口？」

### 2.4 命中率决定一切
> "我会在监控里盯命中率。低于 90% 说明 working set 大于内存或者 key 设计有问题——这时加机器不如改分片键。"

## 3. 数据库与存储选型

**E4 层**：SQL 保一致，NoSQL 好扩展。

**E5 层**——选型必须落在「读/写模式 + 一致性需求 + 查询模式」三个轴上：

| 存储 | 什么时候选 | 代表 | 经典坑 |
|------|-----------|------|--------|
| 关系型（PostgreSQL/MySQL） | 复杂查询、事务、强一致默认 | RDS, Spanner | 单机写上限 → 分库分表代价大 |
| KV（DynamoDB/Cassandra） | 海量写、key 查询、最终一致可接受 | Dynamo | 无法二级查询；分区键设计错=灾难 |
| 文档（MongoDB） | schema 灵活、嵌套读 | Mongo | 事务弱；索引膨胀 |
| 宽列（Cassandra） | 时序、日志、写多 | Cassandra | LWT 性能差；读放大 |
| 全文搜索（Elasticsearch） | 搜索、前缀、聚合 | ES | 近实时≠实时；JVM 运维重 |
| 时序（TimescaleDB/ClickHouse） | 监控指标 | ClickHouse | 更新难 |
| 对象存储（S3） | 大文件、不可变 | S3 | 不是数据库；列表操作贵 |

**选型话术**：
> "写 QPS 20K、按 user_id 点查、最终一致可接受 → Cassandra/DynamoDB 合适。如果团队只有 MySQL，分 64 个逻辑库也能扛，代价是跨行事务没了——这里我选 X 因为……"

### 分库分表（Sharding）
- **分片键选择**是核心考题：高基数、查询路径覆盖、避免热点（user_id 好于 auto_increment id）
- 范围分片（好查范围、易倾斜）vs 哈希分片（均匀、范围查询废）——**没有双赢，只有取舍**
- 扩容路径：一致性哈希 / 预分足够多的逻辑片（64→1024）物理迁移
- 跨片事务： Saga / 两阶段提交 / 尽量设计成单片事务（**能用单片解决就别跨片**）

## 4. 复制与一致性

**E4 层**：主从复制、CAP 定理。

**E5 层**：
- **复制是可用性手段，分片是容量手段**——别混着讲
- 同步复制（不丢数据、写慢）vs 异步（快、故障切换丢数据）vs 半同步（折中）——MySQL `semi-sync`、PostgreSQL `synchronous_commit` 就是这个谱系
- **读己之写（read-your-writes）**：用户发帖后立刻刷新看不到自己的帖子 → 会话粘滞到主库 / 读时间戳路由。**社交类题必考**
- CAP 讲人话版："网络分区必然发生，所以你真正选的是分区时保 C 还是保 A。票务系统保 C 拒绝服务；Feed 流保 A 返回旧数据。"
- 一致性谱系：线性一致 > 顺序一致 > 因果一致 > 最终一致——**能说清业务落在哪一档及为什么**

## 5. 消息队列（Message Queue）

**E4 层**：Kafka 解耦削峰。

**E5 层**：
- **投递语义三档**：at-most-once（丢可以）/ at-least-once（不丢但重，**默认档**）/ exactly-once（贵，依赖幂等或事务）
- **幂等是 at-least-once 的解药**：去重 key + 去重窗口 / 数据库唯一约束 / 版本号。讲清「consumer 重启后重放导致重复扣款怎么防」= E5 信号
- Kafka 核心概念：partition 是并行单位、offset 提交语义、consumer group 再平衡抖动、**分区数 = 并行度上限，提前规划**
- 顺序保证只在**单分区**内成立——按 user_id 分区，同用户的消息才有序
- 削峰话术："写 50K QPS 洪峰，DB 只能 10K——队列做缓冲，消费端按能力拉取，代价是延迟从 ms 级涨到秒级，这个延迟业务可接受。"

## 6. CDN 与边缘

**E4 层**：静态资源放 CDN。

**E5 层**：
- 适合：不可变内容（图片、视频、JS bundle）；**不适合**：个性化动态内容（API 响应）
- 中间态：边缘缓存 + 短 TTL（秒级）——"个性化做的只有头部的用户名，那部分客户端拼"
- 失效难题：CDN 刷新是最终一致的——"改了 config 什么时候全网民生效？"是真实事故高发区
- 视频：HLS/DASH 切片天然适合 CDN；转码管道（上传 → 原始存储 → 转码队列 → 多码率 → CDN）

## 7. 其他高频小件（一句话 + 深挖钩子）

- **API Gateway**：鉴权、限流、路由统一入口——"把横切关注点从服务里拎出来"
- **服务发现**：K8s DNS / Consul——"实例动态上下线，调用方怎么知道地址"
- **分布式锁**：Redis `SET NX PX` + fencing token（**为什么需要 fencing token** 是经典深挖题）；或 ZooKeeper/etcd（更稳更重）
- **心跳与故障检测**：超时阈值与误判的 trade-off；脑裂与 quorum
- **布隆过滤器**：存在性近似判断，无假阴性有假阳性——"告诉缓存穿透说不存在的 key"
- **一致性哈希**：见 §1，缓存/分片通用

## 8. 把构件串成话术

面试中每个构件出现时，标准三段式：

> "这里我加一层 Redis 做 cache-aside（**是什么**）。因为读 17K QPS 单库扛不住（**为什么**）。风险是失效风暴，我用 TTL 抖动 + 逻辑过期兜底；命中率我会作为核心 SLI 监控（**坏了怎么办**）。"
